# 0010. Country architecture: frontend piece implemented; CMS/homepage/banner resolution logic added

Date: 2026-09-09

## Decision

Two pieces landed together, closing out the Country architecture's remaining Phase 1 scope:

1. **Frontend `CountryContext`** (delegated agent, `wood-vintage/frontend` commit `6536c70`):
   `wv_country` cookie, `CountryProvider`/`useCountry()`, a `CountrySelector` component, and
   `?country=` threaded through the real storefront pricing surface identified in the spec's
   scoping note (product detail SSR, category/collection listings, cart, checkout) — not the ~19
   files that merely display prices.
2. **CMS/homepage/banner Global→Country resolution logic** (done directly, not delegated,
   `wood-vintage/backend` commit `9c7d0ad`): the data model existed (`countryId` on
   `HomepageSection`/`Banner`/`CmsPage`, added in `0009`) but nothing read it yet.

## Why

Both were the explicit next items in `tasks/TASKS.md` after `0009`. The backend piece was done
directly rather than delegated because doing it surfaced a real schema gap (below) that needed
careful handling, not a large amount of mechanical work — a good fit for direct work rather than
a delegated task with a large blast radius if the judgment call went wrong.

## What was built — frontend

See the agent's own report for the full file list. Notable design decisions, reviewed and
endorsed on inspection (read `contexts/CountryContext.tsx` and `lib/countryPreference.ts`
directly, not just the summary):

- **Context, not Redux** — unlike the existing `ud_gender` Redux slice, a plain React Context can
  be seeded directly from the per-request cookie in the root layout, since (unlike Redux's
  module-singleton store) it isn't shared across concurrent SSR requests. Avoids the
  `initialized`-flag flash-avoidance dance the gender slice needs.
- **No hardcoded "IN" fallback** — an unresolved country simply omits `?country=`, which the
  backend already treats as default-country pricing. Correctly reasoned: hardcoding a country code
  as a magic fallback would silently break the day the default country changes in admin.
- **Self-healing stale cookies** — a `wv_country` cookie naming a since-disabled country is not
  trusted blindly; it's validated against the live `GET /countries` response and corrected
  automatically, specifically because the backend hard-400s `POST /orders` for an unknown country
  and checkout needed to never hit that path from a stale cookie.
- **Didn't add dead `?country=` params** — checked the actual backend product controller before
  wiring the homepage's featured/trending/new-arrivals/best-sellers endpoints, found those don't
  accept `?country=` (only `/products` and `/products/:slug` do, per `0009`), and correctly left
  them alone rather than adding parameters the backend would silently ignore.

## What was built — backend (CMS/homepage/banner resolution)

`src/utils/countryContent.ts`, two resolution shapes:

- `resolveCmsPage(slug, countryId)` — single-item lookup, country override wins, falls back to
  the global row.
- `resolveHomepageSections`/`resolveBanners(countryId, extraWhere)` — list-level fallback: if the
  country has ANY of its own rows, that whole set replaces the global set; with none, use global.
  Coarser than per-item override, but correctly matches what the schema actually models — these
  are unkeyed content lists (a homepage section has no stable identity a country variant could
  "override" against), not records like `Product` with an id an override table can point at.

**Real gap found and fixed along the way**: `CmsPage.slug` was still globally `@unique` from the
prior commit — this would have made a country-specific "about" page structurally impossible to
create alongside the global one under the same slug, defeating the entire point of the Global→
Country model for CMS pages specifically (HomepageSection/Banner were unaffected — they're
unkeyed lists with no uniqueness constraint to begin with). Fixed: unique per `(slug, countryId)`
instead. One real wrinkle documented in the code and worth remembering: MySQL's unique indexes
treat multiple `NULL`s as distinct values, so the composite constraint does *not* prevent two
global (`countryId: null`) rows for the same slug — that specific case is guarded in application
code (`upsertCmsPage`'s explicit find-before-create path for the null-country case) instead.

Migration `20260909130000_cms_page_slug_per_country` was generated by hand (`prisma migrate dev`
can't run non-interactively once it needs to warn about a constraint-safety issue, even with
`--create-only`) — written directly, applied to the dev DB, and marked resolved via
`prisma migrate resolve --applied`. Verified no duplicate `(slug, countryId)` rows existed before
applying it (there weren't any — no country overrides existed yet).

## Verification

**Frontend**: independently re-verified beyond trusting the report, given this touches pricing —
confirmed the real commit (`6536c70`), clean `tsc --noEmit` and `npm run build`, DB confirmed
clean (only India enabled, 0 pricing overrides, 0 orders). Then ran my own live end-to-end check
(not just re-reading the agent's numbers): booted both servers, enabled `AE`, created a real
`ProductCountryPricing` override (599/399 → 1499/1299), and directly `curl`'d the SSR product page
with and without the `wv_country=AE` cookie — no cookie correctly showed ₹399/₹599 (base), the AE
cookie correctly showed ₹1,299/₹1,499 (override). Cleaned up (deleted the override, disabled AE)
and confirmed the DB was back to the exact state found.

**Backend CMS resolution**: verified directly against the DB with a throwaway script — no HTTP
server involved, specifically to avoid a port collision while the frontend agent was still running
its own tests concurrently in the same window. Confirmed: global CMS page resolves with no
country; a real AE override wins for AE while the global page stays correct for a no-country
request; an unknown slug returns null (not an error); homepage sections/banners correctly fall
back to the global set when a country has none of its own, and correctly return *only* the
country-specific set (not merged with global) once one exists. All test rows deleted afterward,
confirmed via direct query.
